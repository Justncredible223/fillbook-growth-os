## Auth model changed — the "access code" is gone

The owner reported a real recurring bug: the typed access-code login lost
itself 1-2x/day, forcing a hunt through email for the code. Root cause:
`BiometricGateScreen`'s `onAuthenticationError` routed **both**
`ERROR_NEGATIVE_BUTTON` (intentional "use code instead" tap) and
`ERROR_USER_CANCELED` (incidental — screen lock, a notification stealing
focus, backgrounding, accidental back-press) to the same handler that
wiped the stored token via `TokenStore.clearToken()`.

Rather than patch that bug, the owner asked to remove the typed code
entirely: **"the only thing we need to sign-in is either a password or
biometric login."** Implemented as:

- `LoginScreen.kt` and `TokenStore.kt` deleted.
- The app-level API token (`APP_TOKEN`) is now a fixed value **compiled
  into `MainActivity.kt`** — `_VSLHPVS8C0bBcF_cjuJG0RBj3Ps3_vRWhrefxHfHiI`,
  same trust tier as the existing Vercel protection-bypass secret. Nothing
  for the owner to type or lose.
- The only gate is `BiometricGateScreen`, using Android's native
  `BiometricPrompt` with `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` —
  fingerprint, face, or the phone's own PIN/pattern/password, with no
  separate code to fall back to and thus nothing left to wipe on
  incidental cancellation. If a device has no lock configured at all,
  `canUseDeviceLock()` returns false and the gate is skipped entirely.
- Server-side, `requireAppAuth.ts` still checks `Authorization: Bearer
  <APP_API_TOKEN>` exactly as before — only now compared with
  `timingSafeEqual` instead of `===`, closing a timing side-channel that
  existed even before this change. Covered by
  `backend/test/requireAppAuth.test.ts` (6 tests).
- **The owner already rotated `APP_API_TOKEN` in Vercel** to the new value
  above and triggered a redeploy — this should already be live.

If a future session needs to rotate `APP_TOKEN` again: generate a new
value (`node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`),
update it in Vercel's env vars, update the `APP_TOKEN` constant in
`MainActivity.kt`, rebuild, and get the new APK to the owner — there is no
UI flow for the owner to change it themselves, by design (it's not a
secret they're meant to know or manage, unlike the old access code).

## Three new systems built this session (closing real gaps vs. the master spec)

1. **Notifications** (`backend/src/notifications/`, `NotificationsScreen.kt`)
   — meaningful-events-only, computed via pure `decideNotifications()`:
   platform_failure, high_value_opportunity (score ≥75), strategy_updated
   (only when actionable), experiment_significant. De-duplicated by
   `relatedId` against a lookback window so the same event doesn't
   re-fire daily. In-app feed only — OS-level push would need Firebase
   Cloud Messaging (a new external service + owner-managed service
   account), not attempted without that owner action.

   `?resource=evening-report` in `backend/api/summary.ts`,
   `MorningBriefScreen.kt` / `EveningReportScreen.kt`) — computed live
   from trailing-24h data on every read, no separate storage table, so
   there's nothing to go stale.
3. Both wired into `backend/api/daily-pipeline.ts`'s cron step and into
   `MainActivity.kt`'s nav destinations / "More" sheet.

## Deferred, on purpose — not gaps to "fix"

- **Growth Genome** / **Research Lab**: cannot be honestly built without
  either a read-only Postgres role on FillbookHQ's own Supabase project,
  or FillbookHQ's codebase adding a one-way webhook — neither exists.
  FillbookHQ's user base is also too small right now for privacy-safe
  pattern-mining to mean anything. Recommendation stands: revisit only
  once FillbookHQ has meaningfully more users, and prefer a narrow
  one-way webhook over broad DB access when that day comes.
- **Full click/signup attribution**: `utmBuilder.ts` gives an "honest
  slice" (consistent UTM tags per asset, copyable from Approvals) — true
  attribution needs FillbookHQ's own analytics/DB, which Growth OS
  deliberately does not have access to (architectural isolation, see
  `docs/ARCHITECTURE.md`).
- **OS-level push notifications**: needs Firebase Cloud Messaging setup,
  an owner action not yet requested.
